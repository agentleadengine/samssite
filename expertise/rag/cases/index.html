RAG case evidence

Expertise / RAG

A case is useful only when it names the corpus, metric, latency, access rule, failure, and reviewed outcome.

Retrieval can return wrong or irrelevant context, and generation can still produce unsupported answers. A case needs retrieval and answer evaluation.

What published evidence covers

BEIR is a published retrieval benchmark, not a complete RAG case study. Its zero-shot results use nDCG@10. On the finance dataset FiQA-2018, BM25 scored 0.236 and BM25 plus a cross-encoder scored 0.347. On the scientific citation dataset SCIDOCS, those scores were 0.158 and 0.166. These numbers show that the corpus changes the result. They do not measure answer support, access control, index freshness, or tenant isolation.

BEIR Table 2 reports the FiQA-2018 and SCIDOCS nDCG@10 results above. The benchmark paper also warns that no one method wins across all included datasets.

What remains unknown

There is no public number on this page that predicts performance for your code repository, support articles, internal permissions, controlled documents, or tenant mix. Run the small evaluation in the table. Freeze a representative query set, label relevant documents, test access failures separately, and report retrieval plus answer support. Do not transfer a BEIR score into a production claim.

What to publish with an outcome

Name the date, code revision, model ID, embedding model, chunking rule, index settings, query set, metric, latency percentile, and excluded failures. A sentence such as "quality improved" is not evidence.

Do this today

  1. Choose one case and collect 100 representative questions.
  2. Write the access rule and one failure that must never ship.
  3. Measure retrieval, answer support, abstention, and 95th percentile latency.
  4. Publish the setup beside the result.
