Queva OS: a working paper

This is a living document. I update it as the build changes.

Working paper · 11 min read

Summary

I'm building Queva OS as a business assistant on top of the open-source Hermes Agent from Nous Research. The aim is an assistant an owner can talk to, with private project work, memory, and carefully limited connections to business tools. The current code lets routine preparation proceed and asks for a single-use text approval before supported risky actions. Some actions stay owner-only, and others are refused even with approval. There are recorded development tests and browser checks with synthetic data, but live installation and real-account acceptance are still pending. This paper describes that gap as part of the build. [1] [2]

Why I started

I want to build for a small business owner who needs work done and needs to trust how it gets done. Drafting is useful, but the intention here includes taking supported actions in the owner's tools. The lesson I'm taking from the build is that an assistant blocked from everything is "just a chatbot." That is a design problem I still have to solve carefully. [1]

I've had to work between two needs: let the assistant prepare useful work, and keep the owner in control of consequential steps. Connecting an account should not quietly become permission for every action in it. The current approach separates permission to use a connection from approval of a particular change. [1]

I'm treating this as a working paper because those boundaries are still changing. Browser access, in particular, has forced me to be more precise about what an approval actually covers. I can describe the controls in the code. I can't yet claim they have passed live acceptance across a business owner's accounts. [1]

What Queva OS is

Hermes Agent supplies the underlying agent runtime, persistent memory, skills, scheduled work, and messaging gateway. I didn't build those foundations. Queva adds a named business profile, guidance for common work, messaging policies, private project folders and links, saved owner preferences, support controls, and approval rules around supported actions. [1] [2]

The guidance covers inquiry drafts, payment reminder drafts, reviews, paperwork, marketing, and dashboards. Installing that guidance does not connect an app or enable an external action. A pack can describe how to approach a task while the capability needed to finish it is still unavailable. [1]

Hermes also supports MCP, a way to expose tools from another service to the assistant. Queva's reviewed connections narrow which tools may be used and which effects need approval. A tool appearing in a directory is only a setup option. It isn't proof that an account is connected or a task has succeeded. [1] [5]

The choices I'm making

The owner owns it

My intended arrangement is an owner-owned server in Europe and an owner-owned, spending-capped OpenRouter key. The onboarding documents assign billing, data, and credentials to the owner. They also describe removing my setup access at handoff. These are intended arrangements and documented steps, not verified ownership or completed handover for a particular live installation. [1]

Keeping files on that server doesn't mean every piece of data stays there. Model prompts, search queries, selected synced files, forwarded messages, and approved website files can go to their respective providers. Retention and provider permissions still need to be filled in for the actual setup. I need to explain those routes alongside ownership. [1]

Text it where you already talk

I want the owner to learn the assistant through conversation. The kit has setup paths for iMessage through Photon, Telegram, WhatsApp, Slack, and Signal. Those paths require platform setup and an allowed account; they aren't all enabled by default. Readiness includes receiving a real message from that allowed account. iMessage is intended to use the owner's own account. [1]

Memory should help without hiding its costs

I intend Hindsight long-term memory to be on. The sample configuration selects a local embedded store, but the installer still has an off fallback. So "always on" is my intended configuration, not an unconditional property of every installation. [1]

The official Hindsight plugin documents retaining, recalling, and reflecting on information, with automatic capture of conversation turns. Its embedded mode stores memory locally and does embedding and reranking locally. Extraction and synthesis still need a model; the sample uses OpenRouter for that work. Local storage is only one part of the data flow. [1] [3]

Built-in Hermes memory writes are configured for approval, and Hermes documents staged memory review. I haven't established whether that setting also gates Hindsight's separate automatic capture. The reviewed forget command removes built-in memory entries; it doesn't establish deletion across Hindsight, transcripts, and backups. That distinction remains open. [1] [4]

Prepare freely, ask at the risky step

After connection and capability consent, routine reads, drafting, and allowed form filling generally proceed without a fresh approval each time. Supported sending, publication, and certain account changes stop for owner review. "Free to proceed" here is about permission. Model use can still cost money. [1]

There are hard refusals too. Queva refuses money movement, purchases, bank and payment sites, the owner's personal inbox, and bulk lead deletion. Its own AgentMail inbox cannot send, reply, or forward, even after approval. A text code doesn't turn an unsupported tool into an allowed one. [1]

The business profile also instructs the assistant to refuse sensitive material such as patient records, legal case files, card numbers, bank logins, and recovery codes. Those are behavioral instructions. I don't have evidence of universal content filtering. Routine health probes and usage notices are separate from customer messages and don't use the numbered action approval. [1]

How approval by text works

For a supported risky step, Queva stops and sends the owner a preview of the exact action with a random four-digit code. A longer preview can use the private page. The owner approves with YES and the code, or cancels with NO and the code. Only the configured owner's own direct chat and sender identity can approve. [1]

For example, an approval request for an unchanged, reviewed WordPress draft might read:

Publish this reviewed draft to the connected WordPress site? Reply YES 1234 to approve or NO 1234 to cancel. This request expires in 15 minutes.

That is an illustrative request, not a record of a live publication. The owner uses the code actually sent. Approval is single-use and expires after 15 minutes. It covers the exact action, its contents, and the connected account. Changing the connection invalidates pending approvals. Changing a reviewed browser page or form requires fresh approval. [1]

The assistant then retries the identical action. It receives the approval result rather than the code itself. This is implemented for supported actions, not a blanket promise about every possible website effect. Permission for temporary operator access uses a separate process; approving an action is not approving server access. [1]

Costs and monitoring

The owner is instructed to set the spending cap at OpenRouter. Queva's key connection stores and validates the key; it does not create or verify that provider-side cap. I don't have a measured running-cost or savings claim to put here. Memory extraction and other configured model work can add usage. [1]

An operator-side watcher is configured to run hourly on my Mac. It texts me when a watched client key has spent more than $3.00 that day, when usage reaches at least 75%, 90%, or 100% of its cap, or when total OpenRouter account credit falls below $20.00. It watches selected client keys, not every arbitrary key. [1]

Those are alerts to me, not action approvals or a local spending limit. The client-side bill guard is a separate daily check. The hourly configuration and a no-network self-check were reviewed, but whether the job is currently loaded and has delivered live alerts wasn't checked. Full coverage of memory and helper usage is also unverified. [1]

What I've learned building it

The visible approval review series went through 15 rounds. Follow Up Boss had three separate security-fix rounds. Those counts describe recorded review work. They don't amount to an independent security certification or one combined count for the whole project. [1]

The recurring problem was making sure the approved preview matched the real effect. Reviews found incomplete previews, uncertain records, account changes that left approvals alive, and business-app behavior beyond the visible draft. Campaign review had to include the sending accounts and full sequence. Website publication had to account for rendered content and settings. Contact changes had to account for automatic outreach. [1]

Browser policy also changed. An earlier approach left consequential actions to the owner. The current approach permits reviewable actions on approved sites through the text gate. It still has a documented limit: a website can attach invisible behavior to clicks or typing. The gate covers steps Queva recognizes as risky; complete prevention of unapproved website effects is not established. [1]

That is why I prefer reviewed connectors for consequential work where they exist. Their supported operations can have explicit account, content, and effect checks. They still need review of provider behavior, especially automations. The advantage is a narrower action to examine, not a claim that using a connector makes every change safe. [1]

The candidate's inspected test runner lists 41 shell scripts and 48 explicit Python invocations before ShellCheck. Those are 89 top-level invocations, not 89 individual test cases. That aggregate wasn't rerun in the research pass, so a freshly passing total for this candidate is unknown. [1]

A separate development handoff records a passing suite and actual Chromium desktop and phone checks using synthetic data. A reviewed lease download matched the expected file, left the signature empty, consumed approval once, and rejected replay. That's useful evidence for that flow. It doesn't establish live-provider acceptance for this candidate. Focused research checks also confirmed the usage watcher's self-check and TickTick's blocked access. [1]

What is still open

The next work includes installation, real accounts, and clearer data handling. I want this list beside the implemented behavior so a reader can see where my evidence stops. [1]

  • Live acceptance. A clean Ubuntu installation, real CRM connection, owner chat, and live weekly delivery still need verification. Development checks do not close those items.
  • TickTick access. The setup entry and managed permissions disagree. Authentication and successful task changes have not been exercised.
  • Browser limits. Hidden website behavior remains a category of risk. The text gate is not a universal browser guarantee.
  • Memory and retention. Hindsight capture approval and deletion across memory, transcripts, and backups are unverified. Provider retention and scopes still need actual setup decisions.
  • Installation and handover. The exact deployed software pin, remaining provider-configuration inconsistencies, and end-to-end access revocation need proof. General encrypted backups remain listed as unfinished, although a narrower database backup exists.
  • Operational checks. Live alarm delivery and terminal recording acceptance remain unverified. Pause is established for new chat work, not every background timer.
  • Further document and reporting work. E-sign, DOCX, profit-and-loss PDF extraction, scheduled CRM comparisons, and the meaning of Follow Up Boss weekly outcomes remain open in the separate development handoff.

I haven't verified time saved or live business results. For now, I can show inspected behavior, recorded tests, and the remaining questions. I'll update this paper as those questions get real answers. [1]
