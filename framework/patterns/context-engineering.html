Context engineering

Track
Builders · pattern
Time
About 20 minutes
You need
An agent task and a way to inspect its inputs
Last checked
28 Sep 2026

Context engineering is the practice of deciding what an agent sees, when it sees it, and what it carries forward. It is less about finding a perfect prompt and more about giving a capable model the smallest high-signal working set for the decision in front of it.

Context is a finite resource

Anthropic's engineering post on context engineering makes a simple point worth taking seriously: a long context window is not an excuse to paste everything in. Models have an attention budget. More tokens can add relevant evidence, but they can also bury the instruction, repeat stale decisions, and make retrieval less precise.

Anthropic describes context as a finite resource: as token volume grows, attention becomes harder to focus. The practical goal is informative, tight context rather than maximum context.

Checked28 Sep 2026Source 01

Think of every system prompt, search result, tool output, example, and previous message as a candidate for a limited desk. Put the work order, constraints, and evidence needed for the next action on the desk. Leave archived logs, unrelated reference material, and speculative rules in a place the agent can retrieve later.

Set the system prompt at the right altitude

Too much detail turns a prompt into brittle pseudo-code. Too little says “be helpful” and hopes the model invents the operating rules. The post calls the middle the right altitude: clear, direct guidance that supplies strong heuristics without trying to script every branch.

<background>
You are reviewing a pull request for a web application.
</background>

## Instructions
Review only changed application code. Report security, correctness, and test risks.
Do not edit files. Cite a path and evidence for each finding.

## Output
Return findings ordered by severity, then open questions.

Sections and headings help people maintain prompts and help the model identify purpose. Start with the minimal version, test it against real failures, then add an instruction or a canonical example that addresses a demonstrated gap. Do not add a long exception list just because it feels thorough.

Anthropic recommends the minimal information that fully outlines expected behavior, with prompts organized into clear sections and improved from observed failure modes rather than by adding a laundry list of edge cases.

Checked28 Sep 2026Source 01

Design tools as context controls

Tools decide both what an agent can do and how efficiently it learns. A well-named get_customer_by_id is easier to choose than a broad database tool. Return the fields needed for the decision, not a giant object the agent must search mentally. Make inputs descriptive, validation explicit, and errors actionable.

Examples are also context. A few diverse, canonical examples teach an output shape better than paragraphs of abstract instructions. Keep them close to the behavior they demonstrate, and replace an example when the underlying policy changes.

Retrieve just in time

Instead of loading a whole repository or knowledge base before work starts, give an agent identifiers: paths, indexes, saved queries, or links. Let it search and open the relevant material as the task develops. This is just-in-time retrieval. It supports progressive disclosure, where each small discovery informs the next search.

# A useful retrieval path for a code task
1. List the project directories.
2. Search for the route or function named in the task.
3. Open the implementation and its focused tests.
4. Read only the configuration that affects that path.
5. Record the decision and source paths before making a change.

This approach can be slower than loading a precomputed bundle, and the agent needs competent search tools and naming conventions. A hybrid is often better: provide stable project instructions up front, then retrieve changing or large material only when it becomes relevant.

Anthropic describes just-in-time context as keeping lightweight references such as file paths, queries, and links, then using tools to load relevant data at runtime. It can reduce context pollution and support incremental exploration.

Keep long work coherent

Long tasks need a deliberate handoff. Compaction summarizes a near-full conversation into a new context window, keeping decisions, unresolved bugs, and implementation details while dropping repeated messages and obsolete raw tool output. Tune compaction for recall first. A beautiful short summary that loses the key constraint is worse than a slightly longer one.

Structured notes add durable memory outside the active context. A simple NOTES.md or task record can track goal, completed work, decisions, evidence, and next steps. Update it at meaningful milestones, not after every trivial tool call. The next agent or resumed session should be able to orient itself without replaying the entire transcript.

Subagents are another context boundary. Let a specialist search deeply in a clean window, then return a concise report to the lead agent. The lead keeps the plan and integration decisions. The specialist keeps the investigative detail. This division is especially useful for parallel research or independent review.

My take: treat a note as an engineering artifact, not a chat recap. Record the decision, why it was made, the evidence location, and what would invalidate it. That is what makes the next context trustworthy.

My takeFor long-running work

A practical checklist

  • State the task, success condition, and stop condition first.
  • Keep the system prompt at a clear but non-brittle altitude.
  • Offer a minimal tool set with distinct names and compact results.
  • Use a few canonical examples rather than an exhaustive rulebook.
  • Load large or changing material through targeted retrieval.
  • Compact before context gets noisy, not only when it overflows.
  • Persist decisions and open questions in structured notes.
  • Use subagents for focused exploration, then ask for a condensed evidence-based handoff.

Do this today

  1. Take one agent task that feels unreliable.
  2. Remove one irrelevant context source and add one missing success criterion.
  3. Replace one broad tool result with a focused query or retrieval step.
  4. Run the same example twice and compare whether the output became easier to review.
