Local and open models with Ollama

Track
Builders · tools
Time
About 20 minutes
You need
A computer with enough memory for your chosen model
Last checked
28 Sep 2026

Ollama runs models through a local command line and local API. It is a practical way to try open-weight models, prototype an offline workflow, or keep a narrow task on a machine you control. It does not make hardware limits, evaluation, or data handling disappear.

Install and run a first model

Ollama publishes installers for macOS, Windows, and Linux. Use the official installer for your platform, then run a model by name. The first run downloads the model, then opens a chat in the terminal.

# macOS or Linux
curl -fsSL https://ollama.com/install.sh | sh

# Windows PowerShell
irm https://ollama.com/install.ps1 | iex
ollama run gemma4

Ollama documents ollama run for running local models and a local REST API at http://localhost:11434/api. Local API requests do not need an authorization header.

Checked28 Sep 2026Source 01

Choose a model deliberately. A smaller model can be a fine fit for classification, extraction, or a constrained assistant. A larger model may produce stronger results, but it needs more memory and can be slower. Test the actual prompt and documents you care about instead of selecting from a headline.

Call the local API

Ollama's local server is useful when a command line chat is no longer enough. This documented chat request asks a local model a question and turns streaming off so the response comes back in one JSON object. Read the answer from message.content.

curl http://localhost:11434/api/chat -d '{
  "model": "gemma4",
  "messages": [{
    "role": "user",
    "content": "Why is the sky blue?"
  }],
  "stream": false
}'

The local base URL is different from Ollama's direct cloud API. A local application points to http://localhost:11434/api. Keep it local unless you have designed network access, authentication, and monitoring around it. A loopback URL is not a public deployment plan.

from ollama import chat

response = chat(model='gemma4', messages=[
  {'role': 'user', 'content': 'Why is the sky blue?'},
])
print(response.message.content)

Open families worth knowing

“Open” is not one license or one capability level. Check the model card, terms, sizes, languages, modalities, and deployment requirements before selecting one. The following are current family-level facts, not a performance ranking.

Checked open or open-weight families include Meta's Llama 4, Qwen3, DeepSeek R1, Z.ai's GLM releases, Moonshot's Kimi family, Google's Gemma 4, and Mistral's current model families. Each project publishes its own model and usage details.

Ollama's library is where you find runnable tags. The upstream family page tells you what the model is. Those are different jobs. A convenient local tag does not replace an evaluation of the original model's limitations or terms.

My take: local versus hosted

My take: local models are most attractive when privacy, control, repeatable cost, and offline operation matter more than getting the strongest general result on every prompt. Hosted models are often simpler when you need leading capability, long context, elastic capacity, or no device management.

My takeChoosing a deployment shape

The privacy upside is real but conditional. With a downloaded model and local API, the prompt and response need not leave the machine through that inference call. Your application can still send data elsewhere through logging, browser extensions, backups, telemetry, integrations, or a cloud model setting. Check the whole path, not just the model runner.

Local inference shifts work onto you. You own model downloads, storage, updates, hardware capacity, runtime availability, access to the API, and evaluation. A hosted API shifts much of the operational burden to the provider, while adding vendor dependence, network transfer, and usage-based cost. Neither arrangement proves a model is correct.

Evaluate before you depend on it

Make a small evaluation set from the requests the workflow will really receive, with sensitive material removed or anonymized. Include an ordinary case, an ambiguous case, and a case where the correct answer is “I do not know.” Compare usefulness, factual support, formatting, latency, and failure behavior. Re-run the same set after changing the model tag, prompt, hardware, or integration. This is more informative than a single impressive demo.

For a workflow that will extract or classify data, define the expected structure and have code validate it. For a drafting workflow, let a person compare a local response with the current hosted baseline. Keep the local model when it earns its operational cost for the task, not because “local” is automatically safer or cheaper in every setting.

Mistakes I see often

  • Calling a model “private” without checking the app around it. Inspect logs, integrations, and network settings.
  • Choosing only by parameter count. Test task quality, latency, memory use, and failure behavior.
  • Exposing port 11434 to a network by accident. Treat network access as a security design decision.
  • Skipping model terms. Open-weight availability does not make every use identical.

Do this today

  1. Install Ollama and run ollama run gemma4.
  2. Send one harmless prompt to the local API with the curl request above.
  3. Write down the data path from your application to the model and back.
  4. Compare a local and hosted result on five representative, non-sensitive examples before choosing a production workflow.
