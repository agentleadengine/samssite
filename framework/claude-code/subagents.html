Subagents

Track
Builders · Claude Code
Time
About 25 minutes
You need
Claude Code and a project to inspect
Last checked
28 Sep 2026

A subagent is a specialized Claude Code worker with its own context window and rules. Use one when a focused investigation would otherwise fill your main conversation, or when a task needs a tighter tool boundary.

What a subagent does

The main conversation delegates a bounded job, then receives the result. That separation is the useful part. A reviewer can search a large repository and return findings without carrying every search result into the conversation that is planning the work.

Claude Code subagents run specialized work in separate context windows and can have their own tools, permission mode, model, MCP servers, skills, hooks, memory, and worktree isolation.

Checked28 Sep 2026Source 01

I use them for research, read-only review, and a second pass on a narrow problem. They are not a substitute for a clear task. Give each one an outcome, boundaries, and the form of answer you expect.

Choose where it lives

LocationUse it whenWho can use it
.claude/agents/review.mdThe job belongs to this repositoryEveryone using the project
~/.claude/agents/review.mdThe job is a personal reusable helperYou, across local projects
claude --agents '{ ... }'You need a temporary definitionThat session only

Claude Code scans project and user agent folders recursively. A project definition is normally the better team choice because it can be reviewed in version control. Keep names unique. When matching project agents exist in nested folders, the one nearest the current working directory wins.

File-based agents use YAML frontmatter followed by a Markdown system prompt. Their name and description are required, and files are discovered from .claude/agents/ or ~/.claude/agents/.

Build a read-only reviewer

Create the project folder, then save the example as .claude/agents/security-reviewer.md. This agent cannot edit or run shell commands. It can inspect code and return evidence, which is a good first contract.

mkdir -p .claude/agents
---
name: security-reviewer
description: Reviews a requested area for security risks. Use after code changes or when asked for a read-only security review.
tools: Read, Glob, Grep
model: sonnet
maxTurns: 12
---

You are a read-only security reviewer. Inspect only paths relevant to the task.

Return a Markdown report with:
1. Findings ordered by severity.
2. A file path and concise evidence for every finding.
3. A practical remediation direction, without editing files.
4. Open questions and anything you could not verify.

Do not make changes.

The frontmatter is the control surface. tools is a comma-separated list or YAML list. disallowedTools removes inherited tools. model, permissionMode, maxTurns, skills, mcpServers, hooks, memory, and isolation are optional. Spell fields exactly as documented because unknown fields are ignored.

Invoke and scope it

In Claude Code, ask: “Use the security-reviewer agent to review the authentication changes.” Claude delegates when the description fits. The transcript shows a tool call with the agent name and task. You can also define a temporary agent when launching Claude Code:

claude --agents '{
  "docs-reviewer": {
    "description": "Reviews documentation for accuracy and gaps.",
    "prompt": "You are a read-only documentation reviewer.",
    "tools": ["Read", "Grep", "Glob"],
    "model": "sonnet"
  }
}'

Scope tools to the job, not to an idea of maximum autonomy. For a reviewer, omit Edit and Bash. For changes that must not touch the parent checkout, use isolation: worktree. Require a report with evidence rather than a stream of loose notes.

Skills and subagents solve related but different problems. A skill packages reusable instructions. If a skill declares context: fork, Claude Code runs that skill in a forked subagent context. A subagent file gives a named specialist its own configuration. Use a forked skill for a repeatable workflow and an agent for a durable specialist role.

How to make the handoff useful

Delegation only helps when the return is smaller and more useful than the exploration it replaces. Tell the agent whether you need a recommendation, a list of options, a patch plan, or a review report. Ask it to separate observed facts from inference. If it searched widely, require it to name the few paths or sources that mattered most so the main conversation can verify the conclusion without repeating the entire search.

Give the agent a stop rule as well. “Do not edit files” is a stop rule. So is “report a blocker if the test cannot run” or “return after finding three representative examples.” Without one, an agent may continue gathering information after the decision is already supported. That burns time and turns a concise handoff into an unreadable transcript.

For a change-making specialist, return control to the main conversation at a review point: after diagnosis, after a plan, or after focused tests. The lead can then decide whether to broaden scope. This is more reliable than asking one agent to independently search, decide, edit, test, and deploy across an unfamiliar codebase.

Mistakes I see often

  • Giving a reviewer write access. Read-only tools make the promise real.
  • A vague description. State when Claude should delegate, not just the role name.
  • Duplicate names. One agent tree should have one definition for each name.
  • No answer format. Require evidence, open questions, and an ordered result.

Do this today

  1. Pick one repetitive research or review job.
  2. Create a read-only agent in .claude/agents/ with a specific description.
  3. Run it against one small, known area.
  4. Check that the result has paths, evidence, and unanswered questions before adding more tools.
