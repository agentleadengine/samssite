Hooks, event-driven automation

5 min readLast checked 2026-09-28

Hooks are where Claude Code goes from "a tool you use" to "a system you build on." They're little scripts that run automatically when something happens inside the agent, before a tool is called, when a session starts, when the model finishes thinking. They let you inject your own logic into the agent's loop without modifying Claude Code itself. If permissions are the agent's safety rail, hooks are the agent's instrumentation, automation, and custom glue all at once.

The mental model: hooks as middleware.

If you've worked with web servers, you know middleware: code that runs between the request and the response, doing things like logging, authentication, and rate limiting. Hooks are the same idea, but for an AI agent. Each hook is a script that runs at a specific moment in the agent's lifecycle. The script can observe, modify, or block what's happening.

This is the mental frame: hooks are deterministic checks around agent events. A hook can observe, provide context, modify a supported response, or deny an action according to its event contract.

Hook events change, so use the reference.

~ six hook points across the agent lifecycle ~

The hooks reference is the source of truth for event names, matchers, hook types, and response behavior. Do not treat the examples below as an exhaustive event list.

How a hook is actually wired up.

Configure hooks through the documented hook schema. Event names, matchers, input, and response behavior vary by event, so test a hook with a non-destructive task before making it part of a safety control.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "/path/to/safety-check.sh" }
        ]
      }
    ]
  }
}

What this does: every time Claude wants to run a Bash command, the agent pauses, sends a JSON description of the call to safety-check.sh via stdin, waits for it to return a JSON response on stdout, and then decides based on that response whether to proceed. Exit code 0 = allow; non-zero = block.

The six use cases that cover 90% of real hooks.

~ hook use cases, by impact ~

1. Audit logging (PostToolUse).

Every tool call gets appended to a log file with a timestamp. Answers the question "what did the agent actually do in that 4-hour session?" If something goes sideways, the log is how you find out exactly what happened. Set this up once, on every agent, before you do anything else.

2. Extra safety checks (PreToolUse).

Use a PreToolUse hook for a check that needs more context than a rule can express. It should be small, deterministic, and tested. A hook is a complement to a narrow permission policy, not a replacement for it.

3. Output secret scanning (Stop).

Before the agent's final message is shown or saved, scan it for things that look like API keys, tokens, passwords. If anything matches, redact or refuse. This is how you make sure the agent never leaks secrets back to a user or a log, even if it accidentally reads them from somewhere.

4. Context enrichment (SessionStart).

When a session starts, run a script that gathers useful context and injects it into the agent's system prompt: today's date, recent open GitHub issues, what team is oncall, the URL of your team dashboard. The agent starts every session already up to speed.

5. Notifications (PostToolUse or SessionEnd).

If your agent is running a long task, you probably don't want to sit and watch. A hook can ping Telegram, Slack, or email when a long job finishes, or when something surprising happens. The agent becomes something you check back on, not something you babysit.

6. State sync (SessionEnd).

When the session ends, commit any uncommitted changes, upload your notes to a team page, or write a summary of what was done to a log. The agent becomes a team member whose work is automatically captured.

The hook contract, precisely.

Every hook script follows the same protocol:

  1. Read JSON from stdin. Claude Code writes a description of the event: what tool, what arguments, what the agent is trying to do.
  2. Do whatever work you need to do. Log, call an API, run a check, whatever.
  3. Write JSON to stdout. Tell Claude Code whether to continue, and optionally attach a reason.
  4. Exit 0 to allow, non-zero to block.

The two canonical responses:

# Allow the call to proceed
{ "continue": true }

# Block the call with a human-readable reason
{ "continue": false, "stopReason": "detected a production API key in the command" }

Best practices you'll learn the hard way if you don't just start with them.

  • Keep hooks fast. Hooks run in the critical path of the agent. A 5-second hook means every tool call takes 5 extra seconds. Aim for under 200ms. If you need something slower, make it async (fire and forget; do the real work in the background).
  • Fail open for non-critical hooks. If your logging hook can't reach the log server, don't let that stop the agent. Log locally, retry later, keep going.
  • Fail closed for safety hooks. If your secret-scanner can't run, it should BLOCK. Never let the agent proceed because a safety check was broken. "It's probably fine" is how bad things happen.
  • Log hook errors loudly. A hook that silently fails is a hook that's not doing its job, and you won't know. Every hook should have its own error log.
  • Version hooks with your project. Check .claude/hooks/ into git. Your team inherits the same safety rails you do.

Hooks as the skeleton of autonomy.

Once you start composing hooks, something interesting happens: you're not building an agent anymore, you're building a platform that the agent runs on. PreToolUse for safety. SessionStart for context. PostToolUse for audit. SessionEnd for reporting. The agent itself becomes a service, and your hooks are the middleware that turns it from a chatbot-in-a-loop into something production-shaped.

This is roughly where the line between "I use Claude Code" and "I've built a system on top of Claude Code" gets crossed. The pages on going autonomous depend heavily on hooks, because that's how you make an agent safe to run without you watching.
