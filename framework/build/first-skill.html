Write your first skill

Track
Builders · build guide
Time
About 20 minutes
You need
Claude Code installed
Last checked
28 Sep 2026

A skill is a folder with a SKILL.md file that teaches Claude Code a job you do over and over. You write the steps once, and from then on you type one slash command, or Claude picks the skill up on its own when your request matches. This guide builds a real one in about 20 minutes.

What a skill is, in one minute

A skill is plain Markdown with a small header. The header (YAML frontmatter between two --- lines) tells Claude when to use it. The body is the instructions Claude follows when it runs. The folder name becomes the command: a folder called follow-up gives you /follow-up.

Every skill needs a SKILL.md with YAML frontmatter and Markdown instructions. The directory name (or the name field) becomes the slash command, and the description is what Claude reads to decide when to load the skill on its own. Only description is recommended; every other field is optional.

Checked28 Sep 2026Source 01

Skills replaced the older custom commands. A file at .claude/commands/deploy.md still works, but a skill folder can also hold supporting files, and Claude can load it automatically.

Where skills live

LocationPathWho gets it
Personal~/.claude/skills/<name>/SKILL.mdYou, in every project on this machine
Project.claude/skills/<name>/SKILL.mdAnyone working in the repo, once you commit it
Plugin<plugin>/skills/<name>/SKILL.mdWherever the plugin is enabled, as /plugin-name:skill-name

Start personal, move to project once it works. A skill that lives in the repo is documentation your team actually runs, which is the best kind.

My takeFrom building skills for client workflows

Build one: a customer follow-up drafter

This skill turns rough call notes into a short follow-up email in your voice. It is a good first skill because the input is simple, the output is easy to check, and nothing gets sent automatically.

1. Make the folder

mkdir -p ~/.claude/skills/follow-up

2. Write SKILL.md

Save this as ~/.claude/skills/follow-up/SKILL.md:

---
description: Drafts a short customer follow-up email from rough call or meeting notes. Use when the user pastes notes and asks for a follow-up, recap, or next-steps email.
argument-hint: [customer name]
---

Write a follow-up email to $ARGUMENTS based on the notes in this conversation.

Rules:
1. Follow the tone guide in tone.md in this skill's folder.
2. Under 150 words. Plain English. No exclamation marks.
3. Restate only what was agreed. Never add prices, dates, or promises
   that are not in the notes.
4. End with one clear next step and who owns it.
5. After the draft, list anything in the notes that was unclear,
   under the heading "Check before sending".

3. Add a supporting file

Skills can carry extra files that Claude reads only when it needs them, so they do not cost context the rest of the time. Save a short tone guide as ~/.claude/skills/follow-up/tone.md:

# Tone
- Warm, direct, first names.
- Short sentences. One idea per paragraph.
- Sign off with "Thanks," and the sender's first name.

4. Test it

Start claude in any folder, paste some notes, and run it by name:

/follow-up Maria Lopez

Or just ask, "Can you write Maria a follow-up from these notes?" and Claude should load the skill because the request matches the description. If it does not trigger, the description is usually too vague. Put the main use case first and add the phrases people actually say.

$ARGUMENTS expands to everything typed after the command, $0 and $1 pick single arguments, and the arguments field lets you name them. Claude Code picks up edits to a skill in the current session without a restart.

The frontmatter fields worth knowing

  • description is what Claude reads to decide when to use the skill. Lead with the use case.
  • disable-model-invocation: true means only you can start it with /name. Use it for anything with side effects, like a deploy.
  • allowed-tools pre-approves specific tools for the turn that runs the skill, so it does not stop to ask. Keep the list narrow.
  • context: fork runs the skill in its own subagent, so a long job does not fill your main conversation.
  • model switches the model for that turn, for example a faster model for a simple formatting job.

Pull live data in before Claude reads it

A line that starts with an exclamation mark and a command in backticks runs the command first and pastes its output into the skill. The official example uses it to inline your current git diff:

## Current changes

!`git diff HEAD`

## Instructions
Summarize the changes above in two or three bullets, then list any risks.

Skills follow the open Agent Skills standard, and Claude Code adds its own extensions such as invocation control, subagent execution, and dynamic context injection. Cloud sessions and routines do not read ~/.claude/skills/ on your machine, so commit a skill to the repo if a routine needs it.

Changing28 Sep 2026Source 01

Mistakes I see often

  • A giant body. Once a skill loads, its text stays in context, so every line costs tokens on every turn. Keep the body short and move reference material into supporting files.
  • A description that says what, not when. "Email helper" never triggers. "Drafts a follow-up email from call notes. Use when the user pastes notes and asks for a recap" does.
  • No stop point. If a skill can send, publish, or delete, set disable-model-invocation: true and keep a human approval step in the instructions.

Do this today

  1. Pick one task you have explained to Claude at least three times this month.
  2. Create ~/.claude/skills/<task>/SKILL.md with a description that starts with the use case.
  3. Run it twice with /<task> and once by asking in plain words. Fix the description until all three work.
  4. When it is solid, move it into your project's .claude/skills/ and commit it.
