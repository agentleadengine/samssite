Build an MCP server

Track
Builders · build guide
Time
About 45 minutes
You need
Node.js and a local MCP host
Last checked
28 Sep 2026

An MCP server lets an AI host call tools, read resources, or use prompts from one focused integration. Build the smallest useful tool first. A good first server makes one external capability explicit, inspectable, and easy to turn off.

Start with one tool

MCP is a protocol, not a magic connection to every system. Decide what the host may do, what input it needs, and what result comes back. A weather lookup is a good tutorial shape because it reads public information and has a clear input. Your own first tool might look up an order, search approved documentation, or make a draft.

MCP servers can expose tools, resources, and prompts. Standard transports are stdio for a client-launched local process and Streamable HTTP for a remote endpoint.

Checked28 Sep 2026Source 01

I would start with a read-only tool and a narrow schema. A vague tool named “manage_data” invites guesses. A tool named get_alerts with a required state code gives the model and the reviewer a shared contract.

Set up the TypeScript quickstart

The official quickstart shows the TypeScript SDK with @modelcontextprotocol/server and Zod. Create a folder, install the packages, and use ECMAScript modules. The build script produces runnable JavaScript in build/.

mkdir weather
cd weather
npm init -y
npm install @modelcontextprotocol/server zod
npm install -D @types/node typescript
mkdir src
touch src/index.ts
{
  "type": "module",
  "bin": { "weather": "./build/index.js" },
  "scripts": { "build": "tsc && chmod 755 build/index.js" },
  "files": ["build"]
}

Add the compiler options from the quickstart to tsconfig.json, then create src/index.ts. The real pattern is an McpServer, a registered tool with a Zod input schema, and a stdio transport. This smaller version follows that shape without adding an external API call.

import { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import { z } from "zod";

const server = new McpServer({ name: "weather", version: "1.0.0" });

server.registerTool(
  "get_alerts",
  {
    description: "Get weather alerts for a state",
    inputSchema: z.object({ state: z.string().length(2) })
  },
  async ({ state }) => ({
    content: [{ type: "text", text: `Alert lookup requested for ${state}` }]
  })
);

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("Weather MCP Server running on stdio");
}

main().catch((error) => { console.error(error); process.exit(1); });

Build before connecting it. A server that cannot compile is not an integration yet.

npm run build

Connect it to a host

The official server quickstart demonstrates a local stdio connection in Claude for Desktop. On macOS, edit ~/Library/Application Support/Claude/claude_desktop_config.json, give the server an absolute path, and restart Claude for Desktop.

{
  "mcpServers": {
    "weather": {
      "command": "node",
      "args": ["/ABSOLUTE/PATH/TO/weather/build/index.js"]
    }
  }
}

For stdio, JSON-RPC messages share the process standard streams. A server must not write ordinary logs to stdout because that corrupts the protocol. Use console.error() or a logger that writes to stderr.

Choose a transport deliberately

Choose stdio when one local host launches one local server. It is simple, has no listening port, and works well for a personal development tool. Choose Streamable HTTP when the server must be reachable over the network. Each client message is an HTTP POST to one endpoint; a response is JSON or a request-scoped server-sent event stream.

The protocol meaning stays the same across transports. What changes is deployment, authentication, network exposure, cancellation, and logging. Do not turn a local prototype into a public HTTP service by swapping a transport class and calling it done.

Test the contract, not only the process

Start the compiled server from the exact command the host will use. Then ask for a normal input, a malformed input, and an input that should produce no useful result. Check that the tool description helps the host choose it, that the schema rejects bad data cleanly, and that the returned text explains a failure without exposing implementation detail. A server that starts successfully but returns an ambiguous tool result is not finished.

Keep fixtures for these cases. They become a focused acceptance suite when you add a second tool or replace the backing API. If your tool changes state, test a dry-run or preview path first and make the action result identify exactly what changed. A host should never need to infer whether a write happened from a vague success message.

Security basics that matter

  • Use least privilege. Give each tool only the data and action it needs.
  • Validate input. Schemas are an interface contract, not decoration.
  • Keep secrets out of tool output and logs. For stdio, use environment-provided credentials where needed.
  • Authenticate remote HTTP servers. MCP authorization is optional at protocol level, but an exposed service needs its own proper authorization design.
  • Make writes obvious. Separate read and write tools, and require confirmation for high-impact actions.

My take: add one read-only tool, test its exact response in the host, then add the next capability. A small server with clear boundaries is easier to secure than a broad server that tries to imitate an entire product API.

My takeFirst server advice

Do this today

  1. Name one local, read-only capability worth exposing.
  2. Write its input schema and the text result a person should see.
  3. Build the server and connect it with an absolute path.
  4. Ask the host for the capability and inspect the returned text before adding any write tool.
